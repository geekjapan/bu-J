# Webタスクの失敗原因と修正

修正前の30試行は[元の比較結果](web_benchmark_results.md)に保持しています。この文書の再検証と混ぜて集計しません。

## 原因

- Noulは「ゴール全体に十分な画面か」を尋ねていましたが、共通stateにゴールがありませんでした。現在の画面から次の操作を進められるかを明示し、true/false条件とゴールを同じ質問に渡しました。確率0.90、margin 0.20、support 0.95は変更していません。
- ホテル検索は入力値と検索確定を区別できず、Flightsはカレンダーの移動方向を判断する情報が不足していました。固定3タスクに対して、観測された値・完了条件から次の手順を示します。文字列生成helperにも同じ進捗を渡し、originの編集欄をdestinationと取り違えないようにしました。
- 操作候補の絞り込みが、選択済みカテゴリや入力済み都市、便一覧まで消していました。読み取り用の証拠と実行可能な候補を分けました。便の選択・予約は引き続き候補に入りません。
- Flightsの元の入力欄をクリックすると別の編集欄が開きます。先に編集欄を開いて観測してから、その欄に入力します。autocompleteは古い候補ではなく入力値に一致する候補の表示を待ちます。
- 同名の別都市、個別空港、指定日以外の日付まで候補に含まれていました。都市グループと指定日に候補を限定しました。カレンダー表示中の背景ページのスクロールも候補から外しました。
- 画面遷移を1回の観測だけで判定していました。操作を再送せず、最大40回・約2秒、タスク期限内で読み取りを続け、効果を確認します。個々のCDP呼び出しには既存のtimeoutがあります。
- 入力送信前のstaleも送信後の不確実性と混同していました。ブラウザ側で未送信と確認した`NotDispatched`だけを、永続的な`NOT_SENT`として記録します。その後、新しい観測から判断します。入力送信後の例外や取消記録の書き込み失敗は`UNKNOWN_EFFECT`で停止し、再送しません。再起動時の既存operationとの衝突による再送防止も維持しています。
- 推論中に画面が変わっても、古い判断の棄権を先に適用していました。採用・棄権の前に鮮度を確認し、古い判断では操作せず観測し直します。
- Wikipediaが入力欄を再描画すると物理nodeが変わります。同じ文書内の一意なID、フォーム、入力種別と実際の入力値から同じ論理入力欄だと確認できる場合だけ、入力成功を認めます。IDのない欄や候補が重複する場合、select操作にはこの判定を適用しません。
- Flightsの検索URLへの移動と便一覧の読み込み完了を混同していました。同じ検索URLで比較対象側がWAIT後に成功した証跡と照合し、検索条件が揃ったSearch直後は最大5秒・100回、読み取りだけで結果を待ちます。期限内に結果が出なければ通常の停止判断へ進み、検索は再送しません。

## 実APIによる質問の確認

保存された同じ3画面に対する比較では、元のNoul質問が0.531–0.777、認識条件を明示した質問が0.999以上でした。別途、HTTP 403・ログイン要求・CAPTCHAの3負例は0.002未満でした。これらは質問の確認であり、一般的な校正精度の証明ではありません。
