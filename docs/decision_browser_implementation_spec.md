# Decision Browser 実装仕様

文書ID: DBA-SPEC-001 / 版: 1.2

既知の手順をコードで実行し、曖昧な判断だけを有限選択のDecisionモデルへ渡す。認可・実行・成功判定はコードが担う。本書は実装契約であり、実接続や本番利用の承認記録ではない。

## 対象範囲

- 基本経路は、隔離した合成fixtureの検索・一覧抽出・ページ送り。既定CLIはMockで動く。
- 固定Web経路はGoogle Flights、Wikipedia、ホテルfixtureの検索・閲覧を維持する。Flightsの比較日付は両実装で2027-09-20。
- 汎用経路は任意URL・自然文goal・許可origin・明示したファイルを受ける。入力、フォーム送信、タブ、frame、抽出とファイル転送を扱い、固定タスクの知識を使わない。
- ログイン、CAPTCHA突破、制限回避、任意コード実行、Skillの自己有効化、個人Chromeへの自動接続は対象外。外部への書込みは利用者が依頼した範囲に限定する。
- 汎用plannerは型付き候補と文字列・URLを生成できる。URL・観測済み要素index・許可ファイルを実行前に検査する。生成JavaScript・shell・CSS selectorは実行しない。

## 構成と契約

| 境界 | 必須事項 |
| --- | --- |
| Task / Policy | 呼出元が主体・tenant・goal・許可origin・情報分類・各版・操作数/時間/費用予算を固定する。ページやモデルに変更させない。 |
| Observer | session・tab・frame・文書世代・観測時刻に結び付いた要素参照と判断用事実を返す。ローカル観測と外部送信用の最小化データを分け、切り詰めを明示し、判断に必要な情報が欠けた場合は実行しない。 |
| Skill / Registry | 承認済みの不変成果物から、型付き引数・対象・前提/事後条件・リスク・再試行区分を持つ候補を生成する。候補集合をdigestに束縛する。 |
| DecisionProvider | 候補IDを選ぶだけで、ブラウザを操作しない。goalと必要な進捗・事実を質問へ渡す。ページ本文は非信頼データとして扱う。 |
| Policy / Executor | 現在の主体・対象・引数・版・予算を検査し、実行直前に鮮度と対象を確認する。観測から結果検証までを同じbrowser laneで直列化する。 |
| Verifier / Journal | 独立した事後条件で効果を確認し、送出前の永続記録と復旧を管理する。DONEだけでは成功にしない。 |

基本経路のデータ型は[contracts.py](../src/decision_browser/contracts.py)と[schemas](../schemas/)、汎用経路は[general/models.py](../src/decision_browser/general/models.py)を正とする。未知enum・余分なキー・必須値欠落・不正な数値を拒否する。日時はUTC、期限は単調時計、通貨額は最小単位の整数で扱う。

## 判断モデル

主な実モデルはAzureのMicrosoft-Decision-1。設定済みdeploymentと既存Azure CLIログインを使う。新しいリソースや有料サービスへ自動的に切り替えない。モデル接続は許可済みHTTPSに固定し、TLS検証とredirect拒否を必須とする。接続設定は[README](../README.md)、固定API契約は[vendor/contracts](../vendor/contracts/)を参照する。

- 応答model、質問の型、候補集合、選択値、usageを検証する。確率は有限の0〜1、合計の誤差は1e-3以内、選択値は最大確率の候補とする。
- 採用条件は最大確率 ≥ 0.90、次点との差 ≥ 0.20、state support ≥ 0.95。同率・該当なし・欠落・未知モデルは採用しない。Web経路はoperationと選択されたtargetをそれぞれ検証する。
- provider confidenceとstate supportは別の値として記録し、認可や正解率の保証に使わない。閾値は保留データで校正し、調整用データと最終評価を分ける。
- 独立質問だけをまとめる。他の回答に依存する判断は、コードでその回答を受けてから作る。
- Webの文字列helperはgpt-4.1-miniとし、観測済みの入力欄へ渡す文字列だけを生成する。判断と同じgoal・進捗を渡し、生成後も対象と鮮度を確認する。
- 汎用経路では同じhelperが最大3個の型付き操作候補と構造化抽出を生成する。Decision-1が有限候補から選択し、確率・margin・supportの条件を維持する。

## 実行・停止・復旧

基本経路は承認済みルール、有効な判断cache、Decisionモデルの順で解決する。observe-onlyは操作せず、shadowは提案を比較し既知手順だけを実行する。enforcedは検証済み候補だけを実行する。新モデルはshadow評価後に導入する。未設定の修復先や未知の画面では停止する。

1. 観測し、完了条件・候補・認可・予算を確認する。
2. 判断を取得した後も鮮度を再確認する。古い判断は採用も棄権も適用せず、観測し直す。
3. 操作前にPREPAREDとDISPATCHEDを永続化する。保存失敗時は操作しない。
4. 操作を一度送出し、新しい観測で効果を確認した場合だけVERIFIEDにする。
5. 送信の有無・効果が不明ならUNKNOWN_EFFECTで停止する。キャンセルを外部効果の取消とみなさない。

Web経路のNOT_SENTは、ブラウザが入力送信前と証明できる場合だけ許す。取消記録を永続化してから新しい観測へ進む。入力送信後の例外や保存失敗は再送しない。

汎用経路は外部効果を一律に検証できないため、操作応答をACKNOWLEDGEDとして記録する。完了報告はREPORTED、指定した独立のURL・本文条件が新しい観測に一致した場合だけVERIFIEDとする。自動入力再試行・ダイアログ承認・接続先への再接続は行わず、UNKNOWN_EFFECTまたは既存task-idでは自動再開しない。

operationの一意制約で重複送出を防ぐ。未確定記録を照合するまで再開せず、別task-id・新しいキー・journal削除で回避しない。外部サイトのexactly-onceは保証しない。自動取消・削除によるロールバックも行わない。

モデル呼出し・操作・待機・再観測には上限を設け、都合のよい回答が出るまで質問を繰り返さない。非同期の表示更新は読み取りだけで待つ。Webの操作上限・待機時間は[実行条件](web_benchmark.md)に従う。

## 隔離・情報・再利用

- 専用browser/profileと明示したendpointを使い、所有権を照合する。endpoint探索や障害時の自動乗換えは禁止する。CDPはloopbackまたは認証付き私設経路に限定する。
- モデル通信とブラウザ通信の送信先を別々に制限する。URLのscheme・host・port・path、DNS解決先、redirect、内部IP、iframe・fetch・WebSocket・subresourceを対象とする。未検証経路は有効化しない。ブラウザ内proxyをOSの通信遮断と同一視しない。
- PUBLIC/SYNTHETIC以外の情報は、利用条件と送信承認が揃うまで外部モデルへ送らない。Cookie、password、token、署名付きURL、無関係な個人情報をモデル入力・通常ログへ含めない。
- 操作名だけでリスクを決めず、入力イベントやGETの副作用も扱う。重大操作の拡張には、主体・宛先・入力digest・状態・policy版・期限・一回限りnonceに束縛した署名付き承認が必要。現在の実サービス操作へは拡張しない。
- cacheは既定無効。利用時は主体・tenant・intent・各版・モデル・候補集合・判断に使った全入力をHMACキーに含める。R0/R1のみ、TTLは30秒。古い要素参照・座標・承認を保存せず、ヒット後も現候補へ解決して認可・鮮度を確認する。
- 同じbrowser/journalを複数プロセスで共有しない。複数Worker対応は、排他的所有とlease/fencingを検証するまで対象外とする。
- 生成Skillは候補として隔離し、静的検査・正常/異常試験・独立レビュー・署名/版固定・shadow評価を経て承認する。Plannerへ実行環境や秘密情報の直接権限を与えない。公開fixture鍵を本番の承認根拠にしない。

## 監査と受入

SQLite journalを操作記録の正とし、task・step・主体・各版・観測/候補/要求digest・判断・許可理由・効果・エラー・HTTP状態・時間・usageを関連付ける。未確定費用はnullとする。秘匿化した観測だけでは入力を完全再現できないことを明示する。本番では権限分離した監査転送先・削除制御・保持期限を定める。

受入では次を確認する。

- 期待結果に重複・欠落がなく、observe-onlyの操作数が0である。
- 不正応答、低確率、未知候補、入力注入、古いDOM、権限/版変更、期限切れ承認、通信障害で未許可操作を送らない。
- クラッシュ・再起動・保存失敗・未確定操作で重複送出せず、結果不明を成功にしない。
- 実モデル、実ブラウザ、通信制御、cleanupをそれぞれ実行して確認する。Mock・設定・単体試験だけで接続成功を宣言しない。
- 実装・lock・schema・policy・承認artifactを一組で固定する。起動時の契約差分は停止し、復元時も未確定journalを保持する。

性能は同じタスク・候補・完了判定・browser・通信条件で測り、全失敗/timeout、成功率、誤操作、棄権、時間分布、要求数、usage・費用を残す。性能採用は30種類以上のタスクを各側5回以上測り、調整用と保留用を分ける。成功時の時間は別集計する。単発成功や短い棄権を速度向上とみなさない。

fixture性能比較の基準系は同一Controller/Driverで毎回汎用LLMを使う方式、評価系はルール・cache・Decision・承認済みSkillを使う方式とする。元の性能採用目標は、保留データで成功率95%以上、基準系との差の95%信頼区間下限が−2ポイント以上、p50が基準系の50%以下、p95が80%以下。未測定・標本不足なら達成を宣言しない。本番利用には情報送信・隔離・監査保管・運用の承認が別途必要となる。
